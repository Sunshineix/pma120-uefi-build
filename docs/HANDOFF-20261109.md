## 三、最后的准确问题

`loader` 的 `usb_start()`：signal init event → locate QCOM_USB_DEVICE_GUID → **`USB->stop()` → `USB->start_ex(&set)`（loader 自己的描述符）** → 返回成功（品红）。
但 **DWC3 没有做完整重枚举**：主机保持 vendor 描述符（05C6:900E），设备的 WinUSB 状态 Error，fastboot.exe 找不到 fastboot 接口（FF/42/03）。

**对照**：04:28 时同样的 loader 机制成功出现 `xnuloader`（那时主机按 loader 描述符枚举）→ 之后从未再现。环境/控制器状态差异未定位。

## 四、下一步的确定方向（新会话直接做）

1. **读 vendor 自己的 fastboot 源码**（开源 ABL：`QcomModulePkg/Application/Fastboot`）：它用 `start()`（偏移 8）还是 `start_ex()`？描述符如何设置？它启动前是否调 `stop()`/DWC3 reset？→ 按 vendor 原生顺序改 loader 的 usb_start。
2. **检查 vendor 协议 `start()` 的语义**（当前 loader 只用 start_ex）：可能 `start()` = 用 vendor 缓存的描述符拉起，`start_ex` = 更新描述符表但需要配合 `start()` 或控制器 reset 才生效。
3. **DWC3 层的重枚举**：若 vendor 协议无法强制重枚举，可在 start_ex 前直接写 DWC3 的 DCTL（run stop/start）或 USBCMD，强制 host 看到 disconnect→connect。
4. **对照 04:28**：那次 GBL 会话后 USB 控制器状态（ABL fastboot 的残留）与现在有何不同——可用 `oem memmap` 没用；重点看 GBL 的 fastboot 会话是否留下了不同的 DWC3/PHY 状态。
